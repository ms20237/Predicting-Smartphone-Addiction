# Predicting-Smartphone-Addiction

Solution for the Kaggle **Playground Series – Season 6, Episode 8: "Predicting Smartphone Addiction"** competition. Binary classification — predict the probability that a person is addicted to their phone (`addicted_label`), scored on **ROC-AUC**.

## 1. Dataset

| File | Rows | Cols |

- **No duplicate rows or ids.**
- Target `addicted_label` is already `0`/`1` (no string mapping needed).
- **Class balance is the *opposite* of the EV competition**: 490,474 addicted (**70.94%**) vs 200,895 not addicted (29.06%) — majority-positive this time, not majority-negative.
- **No train/test distribution shift**: KS-test on every numeric column returned p > 0.1 (lowest was `notifications_per_day` at p=0.14).

### Columns

| Type | Columns |

| Numeric (9) | `age`, `daily_screen_time_hours`, `social_media_hours`, `gaming_hours`, `work_study_hours`, `sleep_hours`, `notifications_per_day`, `app_opens_per_day`, `weekend_screen_time` |
| Categorical (3) | `gender`, `stress_level`, `academic_work_impact` |

Ranges: `age` 18–35 (mean 26.6), `daily_screen_time_hours` 0.5–15h (mean 7.64), `social_media_hours` 0–8h (mean 2.47), `gaming_hours` 0–4h (mean 1.46), `work_study_hours` 0–6h (mean 2.37), `sleep_hours` 4.5–9h (mean 6.80), `notifications_per_day` 20–250 (mean 145.9), `app_opens_per_day` 15–180 (mean 102.6), `weekend_screen_time` 0.5–17.6h (mean 9.48).

**Does missingness itself carry signal?** A t-test comparing the target rate between missing vs. present rows was run for every column. Almost none were significant: e.g. `social_media_hours` (p=0.99), `notifications_per_day` (p=0.62), `work_study_hours` (p=0.53). The only borderline case was `app_opens_per_day` (p=0.025) and `sleep_hours` (p=0.057) — both weak. **Conclusion: this data looks Missing-At-Random with respect to the target**, so the safest approach is native NaN-handling in the boosted-tree models (see Section 4) rather than engineering missing-indicator features as if they were informative.

## 2. Signal analysis — what actually predicts addiction

This is the most important section of the EDA, and it's a stark result.

### Numeric features dominate; categorical features are essentially noise

| Feature | Pearson r | Mutual Info | Mann-Whitney rank-biserial |
|---|---:|---:|---:|
| `daily_screen_time_hours` | **0.611** | **0.224** | **0.779** |
| `weekend_screen_time` | 0.590 | 0.207 | 0.762 |
| `social_media_hours` | 0.532 | 0.160 | 0.716 |
| `work_study_hours` | 0.251 | 0.042 | 0.310 |
| `gaming_hours` | 0.205 | 0.030 | 0.244 |
| `app_opens_per_day` | 0.063 | 0.079 | 0.082 |
| `sleep_hours` | 0.043 | 0.013 | 0.054 |
| `notifications_per_day` | -0.012 | 0.087 | -0.016 |
| `age` | 0.004 | 0.009 | 0.005 |
| `gender` (cat) | — | 0.0002 | — (Cramér's V = 0.022) |
| `stress_level` (cat) | — | 0.00002 | — (Cramér's V = 0.006) |
| `academic_work_impact` (cat) | — | 0.00001 | — (Cramér's V = 0.003) |

The three screen-time columns (`daily_screen_time_hours`, `weekend_screen_time`, `social_media_hours`) carry almost all the signal. The three categorical columns carry almost none — even though a chi-square test found `gender` "significant" (p = 7×10⁻⁶⁹), its Cramér's V is only 0.022, a textbook case of **statistical significance without practical significance at N=691k**: with enough rows, even a trivial effect clears a p-value threshold.

### The target looks like it was generated from a near-threshold rule on screen time

Binning `daily_screen_time_hours` into 20 quantile buckets and looking at the addiction rate per bucket:

| Daily screen time | Addiction rate |
|---|---:|
| 0.5 – 3.19h | 23.3% |
| 5.48 – 5.89h | 42.0% |
| 6.32 – 6.8h | 64.0% |
| 6.8 – 7.27h | 69.7% |
| 7.77 – 8.26h | 86.0% |
| 8.7 – 9.12h | 95.4% |
| 9.12 – 9.47h | 99.35% |
| 10.25h+ | ≥ 99.8% |

The rate climbs almost monotonically from ~23% to ~100% as screen time crosses roughly 6–9.5 hours/day, with the steepest jump right around the 7-8h mark. This is a much sharper, more deterministic relationship than the EV competition's `Subsidy_Available` signal — it strongly suggests the synthetic data generator used something close to a threshold/sigmoid rule on `daily_screen_time_hours` (and correlated columns) to assign the label. This single fact explains most of what follows in the model results.

### Feature-feature correlation (redundancy, not leakage)

`daily_screen_time_hours` correlates with `weekend_screen_time` at **r=0.80** and with `social_media_hours` at r=0.60 — the three strongest predictors are also the most redundant with each other. VIF values stayed under 3.1 for every numeric feature, so this isn't severe enough to break Logistic Regression, but it does mean the three "top features" are partly the same signal counted three times.

## 3. Feature engineering (`06_Feature_Engineering.ipynb`)

Original 14 columns → **28 columns** (23 numeric, 3 categorical unchanged):

| Engineered feature | Rationale |
|---|---|
| `missing_count`, `has_any_missing` | Tests whether "didn't answer" itself signals — checked above, weak/no effect, kept as candidate features anyway |
| `stress_ord`, `academic_impact_bin` | Numeric encodings of the (weak) categorical signals |
| `screen_to_sleep_ratio`, `notifications_per_app_open`, `screen_per_notification` | Ratios among the behavioral columns |
| `weekend_vs_weekday_diff`, `leisure_screen_hours` | Decompose `daily_screen_time_hours` into weekday/weekend and work/leisure components |
| `sleep_deficit`, `low_sleep_flag` | Threshold features on `sleep_hours` |
| `heavy_screen_flag` | `daily_screen_time_hours` above the sample median — turned out to be the single most important engineered feature (see below) |

## 4. Cross-validation methodology (`07_Cross_Validation.ipynb`)

- **5-fold Stratified K-Fold**, `shuffle=True`, `random_state=42`, folds cached to `artifacts/fold_ids.npy` and reused by every model script.
- Verified: every fold has positive rate 0.7094, matching the overall rate.

## 5. Model results

Missing values are handled differently per model, since this dataset (unlike the EV one) actually has them:
- **Logistic Regression**: median imputation (numeric) + `"Missing"` category (categorical) — the only model that imputes.
- **CatBoost / XGBoost / LightGBM**: native NaN handling for numeric columns (no imputation); CatBoost's categorical encoder needs an explicit `"Missing"` string, XGBoost/LightGBM's `category` dtype preserves NaN as-is.

| Model | Fold 0 | Fold 1 | Fold 2 | Fold 3 | Fold 4 | **Mean CV AUC** | Std |
|---|---:|---:|---:|---:|---:|---:|---:|
| Logistic Regression (baseline) | 0.91513 | 0.91566 | 0.91657 | 0.91688 | 0.91608 | **0.91606** | ±0.00063 |
| CatBoost | 0.96254 | 0.96295 | 0.96335 | 0.96396 | 0.96297 | **0.96315** | ±0.00048 |
| XGBoost | 0.96309 | 0.96362 | 0.96398 | 0.96478 | 0.96354 | **0.96380** | ±0.00057 |
| LightGBM | 0.96271 | 0.96344 | 0.96387 | 0.96439 | 0.96325 | **0.96353** | ±0.00057 |

**XGBoost was the strongest single model** (0.96380), narrowly ahead of LightGBM (0.96353) and CatBoost (0.96315). All three boosters land within 0.0007 of each other — again pointing to a near-deterministic underlying rule that any reasonable tree ensemble can find. Logistic Regression trails by ~4.8 AUC points this time (vs. ~3.4 points on the EV data) — a bigger gap, consistent with the relationship being closer to a threshold than a smooth linear one, which hurts a linear model more.

### Feature importance — and a striking divergence between models

| Rank | XGBoost (gain) | LightGBM (split count) | CatBoost (PredictionValuesChange) |
|---|---|---|---|
| 1 | **`heavy_screen_flag` (0.968)** | `notifications_per_day` (11,299) | `weekend_screen_time` (19.84) |
| 2 | `daily_screen_time_hours` (0.006) | `app_opens_per_day` (11,132) | `daily_screen_time_hours` (16.54) |
| 3 | `social_media_hours` (0.006) | `weekend_screen_time` (9,365) | `social_media_hours` (14.35) |
| 4 | `weekend_screen_time` (0.004) | `work_study_hours` (8,984) | `notifications_per_day` (12.76) |
| 5 | `notifications_per_day` (0.002) | `gaming_hours` (8,293) | `app_opens_per_day` (11.36) |

**XGBoost puts 96.8% of its total gain on a single engineered feature — `heavy_screen_flag`** (whether `daily_screen_time_hours` is above the sample median). Given the near-threshold addiction-rate pattern found in the EDA, XGBoost essentially discovered it can solve most of the problem with one split and builds the rest of the ensemble on small corrections. CatBoost and LightGBM don't show this concentration at all: CatBoost spreads importance across the raw screen-time columns directly, and LightGBM's split-count importance (a different metric — see the EV README for the same caveat) spreads even further across many features, including ones with weak individual signal like `notifications_per_day`. This is a genuine algorithmic difference, not a bug: XGBoost's greedy per-node gain search latches onto the single feature that most cleanly separates classes early, while CatBoost's oblivious trees and LightGBM's leaf-wise growth build the same overall predictive picture through many smaller, more distributed splits.

## 6. Ensemble (`08_Ensemble.ipynb`)

| Model | OOF AUC |
|---|---:|
| Logistic Regression | 0.91606 |
| CatBoost | 0.96315 |
| **XGBoost** | **0.96380** |
| LightGBM | 0.96353 |
| Simple average (4 models) | 0.96142 |
| **Optimized weighted ensemble** | **0.96425** |

Optimized weights: `baseline_logreg=0.000`, `catboost=0.3185`, `xgboost=0.3139`, `lightgbm=0.3676` — the optimizer correctly zeroed out Logistic Regression's weight (it was dragging the simple average below every individual booster) and blended the three boosters.

**Unlike the EV competition, the ensemble here (0.96425) beats the best single model (XGBoost, 0.96380).** The difference: on the EV data, all three boosters converged on nearly identical predictions (too correlated to blend usefully), but here XGBoost's near-total reliance on `heavy_screen_flag` gives it a genuinely different error pattern than CatBoost/LightGBM's more distributed approach — enough diversity for the weighted blend to add real lift over any single model.

## 8. Conclusion

Three findings define this dataset and this solution:

1. **Screen-time behavior, not demographics, drives the label.** `daily_screen_time_hours`, `weekend_screen_time`, and `social_media_hours` account for nearly all predictive signal (Pearson r up to 0.61, MI up to 0.22). `gender`, `stress_level`, and `academic_work_impact` are statistically detectable only because of the huge sample size (N=691k) — their actual effect sizes (Cramér's V ≤ 0.022) are negligible. If this were a real-world dataset, only the three screen-time columns would be worth collecting for this prediction task.

2. **The addiction label behaves like a near-threshold function of screen time**, not a smooth linear relationship — the addiction rate jumps from ~23% to ~100% as `daily_screen_time_hours` crosses roughly 6–9.5 hours/day. This explains why (a) Logistic Regression underperforms the boosters by a wider margin than in the EV competition, and (b) XGBoost's own engineered `heavy_screen_flag` threshold feature captured 97% of its total gain — the model essentially rediscovered the generating rule.

3. **Missingness here is (mostly) just missingness** — 61% of rows have a gap somewhere, but almost none of that missingness correlates with the target. This justifies relying on each library's native NaN handling rather than spending effort on missing-indicator feature engineering, and it's why the boosters (which handle NaN natively) beat Logistic Regression (which needs imputation) by a wide margin here.

**Practical takeaway**: with a relationship this close to deterministic, further gains are more likely to come from (a) tuning the boundary/threshold features around `daily_screen_time_hours` and `weekend_screen_time` more precisely (e.g. isotonic calibration, more granular ratio features), and (b) stacking rather than simple weighted averaging, than from adding new engineered features on the categorical columns — those are close to exhausted as a signal source.

## 9. Reproducing this pipeline

```bash
pip install pandas numpy scikit-learn scipy statsmodels seaborn matplotlib catboost xgboost lightgbm
```

Run notebooks in order:

1. `01_EDA.ipynb` — dataset checks, missingness analysis, signal analysis (writes `plots/`)
2. `06_Feature_Engineering.ipynb` — writes `dataset/train_fe.csv`, `dataset/test_fe.csv`
3. `07_Cross_Validation.ipynb` — writes `artifacts/fold_ids.npy`
4. `02_Baseline.ipynb`, `03_CatBoost.ipynb`, `04_XGBoost.ipynb`, `05_LightGBM.ipynb` — each writes `artifacts/oof_<model>.npy` and `artifacts/test_pred_<model>.csv`
5. `08_Ensemble.ipynb` — reads all OOF/test predictions, optimizes ensemble weights, writes `submission.csv`
